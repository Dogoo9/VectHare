# Codex implementation task: portable embedding provider migration (phase 2)

## Goal
Finish the portability work merged in #28 in Dogoo9/VectHare. Users should switch their **embedding inference server** (especially KoboldCpp to llama.cpp, retaining the exact same Nomic model) without losing their existing vector collections. If the embedding space changes (for example Nomic to EmbeddingGemma 2), provide a safe **text re-embedding migration** to a NEW collection. Do not conflate embedding inference provider with vector-storage backend (Vectra/Standard, LanceDB, Qdrant). The original collection and its physical locator remain intact until explicit switch-over.

## IMPORTANT: Codex execution and PR
This branch contains a task specification only, not an implementation. In the configured Codex environment, implement, test and commit the code in a separate working branch, then open a **draft** PR targeting `main`. Link the spec and prior PR #28. Do not merge or deploy. Keep the user’s local collection data untouched: you do not have access to it and must not infer or claim that it has been migrated.

## Existing baseline (verify in latest main)
- `core/collection-portability.js`: fingerprint/probe helpers, `storageSettings()`, `collectionStorageKey()`, guarded writes, `rebuildCollection()`.
- `core/collection-metadata.js`: `embedding`, `storageLocator`, `embeddingConnection`, `previousEmbeddingConnection`.
- `core/core-vector-api.js`: client-generated vectors only for `webllm`, `koboldcpp`, `bananabread`; `llamacpp` currently uses server-generated vectors and `requirePrecomputedForReassignment()` blocks cross-source use. `getSavedHashes()` has a chunks metadata fetch that passes `settings.source` rather than the physical routing source; audit all lifecycle operations. Multi-query currently shares one query vector using global `settings` and must not cross incompatible embedding profiles.
- `backends/standard.js`: native SillyTavern /api/vector endpoints and Similharity endpoints pass `source` and model as part of physical routing; some endpoints accept precomputed embeddings. Verify actual server contracts, not guesses.
- `docs/portable-embedding-collections.md`, `docs/portable-embedding-collections-plan.md`, PR #28 and existing tests. The current docs explicitly identify the server/API boundary; investigate whether the existing precomputed-vector API can satisfy the requirement once llama.cpp has a client-side adapter. If companion-server changes truly are necessary, identify the precise contracts, add any safe changes within authorized VectHare repository, and document required upstream work; never claim a working path that the server does not support.

## Deliverables
1. Introduce a unified, tested local OpenAI-compatible `/v1/embeddings` client for llama.cpp and compatible local inference servers; normalize indexed responses, robust errors/timeouts/batching, finite nonzero dimensions, and document/query preprocessing. Preserve existing KoboldCpp behavior. Avoid exposing local private text to remote hosts automatically; no cloud fallback. Do not put API keys in collection exports, logs or fingerprints. Validate URLs/credentials safely.
2. Separate immutable physical `storageLocator` (backend, source namespace, model namespace, ID), logical collection identity, embedding-space fingerprint, and selectable endpoint profile in **all** reads/writes: discovery, hashes, count, query, multi-query, hybrid, edit, inserts, delete, export/import, auto-sync, cache, metadata. Never allow change of inference provider to relocate physical index. Same-name namespaces must remain isolated.
3. Implement per-collection **Embedding Provider / Migrate** action in Database Browser UI. Show current physical storage and embedding endpoint/model, compatibility (compatible/incompatible/unknown) with reasons, preview and estimated work, matching-probe test and a final explicit confirm. Do not offer silent 'force compatible' on incomplete provenance. Explain that 768 dimensions or matching filenames alone prove nothing.
4. Compatible inference switch: if trustworthy provenance/configuration and both document/query synthetic probes verify within a conservative tolerance, query and insert with the new server’s vectors while retaining the original physical collection and its vector-storage namespace. Check model artifact/revision, pooling, tokenization, normalization, prefixes/task modes/truncation/context, distance metric and version. Unknown legacy provenance remains unknown; require a safe rebuild rather than certifying by comparing two currently loaded servers.
5. Incompatible model migration: export/read original chunk text, metadata, activation settings and stable identifiers; re-embed into a distinct target collection/index using target provider; support progress, cancel, batch/retry or clean restart, collision/missing-text checks, thorough post-write count/content/ranking verification, explicit cutover and rollback. No deletion or mutation of source, and no active partially-built index. Preserve lexical and temporal/conditional metadata, locks, groups and collection policy; prevent concurrent autosync corruption.
6. Keep independent explicit BM25 lexical-only fallback (no dense-service call) where lexical index coverage is complete; surface incomplete coverage rather than silently returning partial memory. Existing hybrid behavior should remain compatible.
7. Add tests: KoboldCpp Nomic -> llama.cpp Nomic compatible without reindex and original locator unchanged; same-dimensional incompatible model; missing provenance; same endpoint changing model; query/document preprocessing mismatch; invalid/NaN/zero/misaligned responses; various backend operations after reassignment; mixed-profile queries; rollback/cancellation/failure/retry; old imports; UI state and settings persistence; source/namespace isolation. Use synthetic fixtures. Run current suite and the repository's relevant retrieval evaluation. Note that mocking is not a live migration test.
8. Update user docs with a cautious manual KoboldCpp/llama.cpp verification checklist and exact server/API limitations if any.

## Non-goals/constraints
- No rewrite of retrieval architecture, no Summaryception changes, no new embedding requirement, and no unnecessary dependencies.
- Keep all data and inference local to user-configured endpoints. Codex environment should use synthetic data; never access user's personal conversations or live vectors.
- Do not modify other repositories or make unsupported claims about SillyTavern server capabilities. If an upstream patch is unavoidable, document precise changes and realistic limitations.
- Do not alter or remove any live user collections; do not auto-merge.

## Acceptance
Draft PR contains implementation and tests, documented compatibility/safety behavior, exact test commands and results, limitations, and a manual validation procedure. The existing collection must remain queryable by its original configuration during and after migration, with a rollback path.
